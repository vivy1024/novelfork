# 卷内连写

一次推进多章时用这套规程。它解决的不是"怎么写好"，是"连续跑二十章不跑偏、不失控、断了能接上"。

## 批次按卷切

卷纲里每一卷都有章节范围，**一卷就是一个批次**。不要自己定"写 20 章"这种脱离结构的批量——卷是作者定义的叙事单元，按它切，批次边界天然对齐情节节奏。

一卷太长（超过 30 章）时，按卷内的阶段目标再切。

## 每章的固定动作

**每一章都要重新取上下文，不要靠对话里残留的信息。**

```text
write.preflight   →  确认可写，取回焦点/近章摘要/伏笔/卷纲
scene.spec        →  这一章的蓝图与情节点预算
pipeline.write    →  写
（写后同轮清零）   →  检查、修正、更新状态
```

这样跑，上下文压缩多少次都不影响——设定和进度都在库里，不在对话历史里。

## 什么时候必须停

遇到下面任一种，**停下来报告，不要自行决定跳过或重试**：

- 审计出现 critical 级问题，且同章修正已达 2 次仍不过
- preflight 报出 blocking，且原因需要作者决策（如卷纲缺失、底牌用尽）
- 连续两章出现同类问题（说明是系统性偏差，不是单章失误）
- `pipeline.write` / `chapter.write` 失败，或工具返回字数/体积异常

停的时候要给出：**写到第几章、卡在什么、已经试过什么、需要作者定什么**。

## 什么时候不该停

- 单章的 warning——记录并继续
- 伏笔到期提醒——这是正常的悬念债，不是错误
- advisory 级的文风提示——除非确属问题

停得太勤，连写就失去意义。

## 断点续跑

跑到一半断了（网络、报错、手动停），**不需要从头来**。状态都在库里：章节索引知道写到第几章，叙事记忆知道结算到哪。

续跑时直接跑 `write.preflight`，它会告诉你下一章该写第几章。从那里继续。

## 汇报格式

一批跑完后，汇报要包含：

- 实际完成的章节范围
- 每章的关键事件（一句话）
- 触发过的 warning 及处理
- 未解决的问题和需要作者定夺的点

**不要贴正文全文。** 作者要看正文会自己去翻章节。

## 边界

- 这条管**推进节奏与失败处理**，不管单章写作质量。
- 不要为了跑完批次而降低标准——写不动就停下来说清楚，比硬凑二十章有用。
