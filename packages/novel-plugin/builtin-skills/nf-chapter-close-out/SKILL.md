# 写后同轮清零

正文落盘**不是**汇报时机。每章写完后，必须在同一轮内把检查跑完、把 blocking 清零，才算这一章完成。

## 为什么

连续写多章时，最常见的失败不是写错，是**提前收工**：正文一落盘就汇报"第 N 章已完成"，把审计、伏笔更新、状态结算留到下一轮。下一轮上下文已经压缩过，那些待办就永久丢失了。

章节数越多，这个漏洞越致命。

## 怎么做

正文写入后，**不要停下来汇报**，直接继续：

1. **跑预检与审计** —— 调 `write.preflight` 确认下一章可写；对刚写的这章调审计工具。
2. **看 blocking** —— 有 blocking 就地修正并复查，不要记成待办。
3. **更新状态** —— 伏笔新增/回收、时间线、角色状态变化，本章引起的立刻用 `lore.write` / `memory.settle_range` 写回经纬与叙事记忆，不另存旁路文件。
4. **确认落盘** —— 以 `pipeline.write` / `chapter.write` / `rewrite.apply` 的工具返回为准确认正文已写入；失败或字数异常就重写，不要去磁盘上核对章节文件。

以上全部完成后，才输出这一章的完成汇报。

## 重试上限

同一章的 blocking 修正**最多 2 次**。第 3 次仍不过，停下来把证据交给作者定夺——不要反复重写同一章，那会烧掉预算且往往越改越偏。

## 豁免

作者显式说「本章跳过检查」时，在该章标题行下加一行标记：

```markdown
<!-- 检查:跳过 -->
```

后续的欠账拦截认这个标记。其余检查照常。

## 边界

- 这条纪律管**执行时机**，不管写作质量。质量由审计工具判定。
- 不要因为"想让作者早点看到"就提前汇报——作者要的是写完的章，不是写了一半的章。
