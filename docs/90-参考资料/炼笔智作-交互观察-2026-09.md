## 对 NovelFork 的启示

1. **用任务流程组织已有能力。** 面向作者的入口应是“构思一本书、学习参考稿、写下一章、审这一章”，现有经纬、记忆、工作流画布在对应任务里提供支撑，不再要求新人先理解组件名。
2. **蒸馏有预览、有范围、有产物。** T2.2 先展示切章结果、覆盖范围与预计调用规模；开始后记录可恢复进度。结果形成来源包，逐条带证据与“可迁移 / 作品专属”分类，作者采纳后才影响本书。文风统计只是其中一个输出，不把完成统计等同于完成蒸馏。
3. **参考库与本书设定分开。** 作者明确选择本次使用的来源、预设与范文；经纬的本书事实不被参考作品的人名、世界与情节覆盖。现有 T2.1 的审阅字段为此提供基础。
4. **审与改分开。** T2.5 自审先给问题位置、原句及理由；修改作为可比较的候选由作者决定。检测评分作为可选参考，不承诺通过检测或把检测分数等同于真实作者贡献。
5. **工作流画布面向配置，任务向导面向使用。** 复用已有配方及运行记录，让默认写作流程以少量清晰步骤呈现；需要定制时再打开画布。两种表现共用运行实例和产物，不建第二套执行引擎。

## 本轮结论与边界

这些观察支持完善现有阶段 2、3、4、5 的交互，不需要换技术底座或重新开发通用 Runtime 页面。本轮优先完成文风预设、技能引用与保存可靠性；下一切片以 T2.2 的“输入预览 → 分批蒸馏 → 证据审阅 → 采纳为本书预设”为主。

尚无证据说明该站采用什么后台架构、记忆模型或工作流引擎。没有观察到自动文风预设蒸馏或完整关系图谱的可用过程，不能把这些当作已验证能力，更不能直接据此照搬数据库设计。
