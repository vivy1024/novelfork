# NovelFork 长篇叙事记忆调研

调研日期：2026-10-24。论文元数据经 arXiv API 核实；star 数和许可证经 GitHub API（`/repos/{owner}/{repo}` 的 `license.spdx_id`）核实，数值以调研当天为准。标「未核实」的条目表示没有拿到一手证据。

---

## 1. 结论：最值得借鉴的 8 个机制

| # | 机制（一句话） | 来源 | 对应短板 | 难度 | 能否参考代码 |
|---|---|---|---|---|---|
| 1 | **伏笔/承诺台账 + 增量 delta**：每章写完只调一次 `update`，四个数组：upsert 角色状态、追加事件、新增未兑现承诺、按 key 关闭承诺。写章时注入整个结构化状态，默认不注入前文正文 | NstAgent（arXiv 2609.35759） | 长线伏笔超窗看不见；每章开销线性增长 | 低–中 | 可以，MIT |
| 2 | **伏笔三元组 Foreshadow–Trigger–Payoff**：把伏笔写成可执行的触发谓词，每章检查触发条件是否满足；满足时把 payoff 作为本章约束注入，回收后移出伏笔池 | CFPG（arXiv 2601.07033） | 长线伏笔超窗看不见；hooks 通道只能按时间窗 | 中 | 未找到官方代码仓库，未核实 |
| 3 | **场景级状态转移校验**：写前生成 Pre/Post/Forbid 三组谓词，前置条件不被当前记忆支持就不写；写后检查是否实现了 Post、有没有违反 Forbid；有冲突只改冲突句，通过后才写入动态记忆 | ConWriter（arXiv 2608.05169，EMNLP 2026 Findings） | 一致性检查只是正则；写前召回不强制 | 中–高 | 可以，MIT |
| 4 | **递归摘要树 + collapsed-tree 召回**：章 → 卷/篇章 → 全书逐层摘要；召回时把所有层的节点放进同一个池子，按相似度在 token 预算内取 | RAPTOR（arXiv 2401.18059）；ReadAgent 的 gist + 回查原文（arXiv 2402.09727） | 没有卷级、全书级层级摘要 | 中 | RAPTOR 可以，MIT；ReadAgent 代码许可证未核实 |
| 5 | **事实带有效期，失效不删除**：每条事实有 valid/invalid 时间窗，信息变化时把旧事实标为失效，保留历史。NovelFork 可用章节序号作时间轴，在 SQLite 里实现 | Graphiti / Zep（arXiv 2501.13956） | state、timeline、knowledge 三个通道的「第 N 章时谁知道什么」；可撤销 | 低–中 | 可以，Apache-2.0；只借数据模型，不借图数据库 |
| 6 | **混合召回融合**：BM25（SQLite FTS5）+ 实体命中 + 可选向量，多路打分后融合。设定条目也走这条路，不再全量注入 | mem0 README；Graphiti；MemOS 本地插件（SQLite + FTS5 + 向量）；SCORE（TF-IDF + cosine，arXiv 2503.23512） | 设定条目全量注入 | 低 | mem0 / Graphiti / MemOS 都是 Apache-2.0，可以 |
| 7 | **重要度 × 新近度 × 相关度打分，加阈值触发反思**：三项各归一化后等权相加；最近事件的重要度累计超过阈值（原文 150）时触发更高层的总结。NovelFork 可以用它决定什么时候生成卷级摘要、哪些事实升级为长期记忆 | Generative Agents（arXiv 2304.03442） | 层级摘要何时生成；facts 通道排序 | 低 | 只参考论文；官方代码许可证未核实 |
| 8 | **按错误分类做检查器，并用错误密度做回归评测**：ConStory 定义 5 大类、19 子类错误，每条判断都要附原文证据，按每万字错误数（CED）计分。FABLES 发现 LLM 评审在检测不忠实陈述上和人工标注相关性都不强，所以机器检查结果必须给证据，交给作者裁决 | ConStory-Bench（arXiv 2603.05890）；FABLES（arXiv 2404.01261） | 一致性检查只是正则；缺乏可量化的回归基线 | 低 | ConStory-Checker 代码和数据集的许可证未核实 |

补充两条工程做法，来自开源工具，不来自论文：
- **写前门禁和变更声明协议**：模型输出必须带结构化变更声明（`---CHANGES---` + JSON），引用了不存在的实体就打回。来源是天命（README 声明 MIT，但 GitHub 没识别到 LICENSE 文件，按未核实处理）。千笔一文的「must 契约」也是这个思路，MIT。对应短板：写前召回不强制。
- **稳定前缀，提高缓存命中**：全书级前缀（设定、must 规则、常驻条目）逐字节保持不变，章级前缀放在后面。来源是千笔一文（MIT）。它在 README 里自称每章总成本降 29%，但这是作者自报，不是独立实测。对应短板：每章开销增长。

## 2. 论文清单

### 2.1 长篇生成

- **Re3**（2022，EMNLP）https://arxiv.org/abs/2210.06774
  - 机制：先生成结构化总纲，写每段时从总纲和当前故事状态里取上下文重新拼提示词；生成多个续写候选，按情节连贯和前提相关度重排；最后再做一遍事实一致性编辑。
  - 结论：人工评测中，情节连贯 +14%，前提相关 +20%（绝对值）。
  - 对 NovelFork：「生成 → 重排 → 一致性编辑」可以做成章后审核的可选步骤。
  - 代码：MIT。

- **DOC**（2022/2023，ACL）https://arxiv.org/abs/2212.10077
  - 机制：更细的层级大纲（detailed outliner），加上在生成过程中强制贴合大纲细节的控制器。
  - 结论：相比 Re3，情节连贯 +22.5%，大纲相关 +28.2%，有趣度 +20.7%；人类评价它更可控。
  - 对 NovelFork：把创作负担前移到大纲层。卷纲、章纲应该进入 hard 或 timeline 通道，而不是只当参考。
  - 代码：MIT。

- **RecurrentGPT**（2023）https://arxiv.org/abs/2305.13304
  - 机制：用自然语言模拟 LSTM。长期记忆存盘，短期记忆放在提示词里，每段更新一次；记忆是人类可读、可编辑的。
  - 结论：只有定性展示，没有找到量化指标。
  - 对 NovelFork：印证「记忆可读可改」符合作者权威的方向。
  - 代码：GPL-3.0，不能进仓库。

- **Dramatron**（2022）https://arxiv.org/abs/2209.14958
  - 机制：分层提示词链，依次生成 logline、标题、角色、场景节拍、地点、对白。
  - 结论：15 位影视和戏剧从业者参与用户研究，结论是定性的。
  - 对 NovelFork：分层生成和逐层确认的交互模式。
  - 代码：Apache-2.0。

- **Agents' Room**（2024，ICLR 2025）https://arxiv.org/abs/2410.02603
  - 机制：规划 agent（情节、冲突、角色、场景）和写作 agent 分工，通过共享 scratchpad 协作；同时发布了 Tell Me A Story 数据集。
  - 结论：专家评审更偏好它生成的故事。
  - 对 NovelFork：「共享 scratchpad」相当于结构化状态，规划和写作在这里分离。
  - 代码：未找到官方仓库。

- **LongWriter / AgentWrite**（2024）https://arxiv.org/abs/2408.07055
  - 机制：作者发现输出长度受限于 SFT 数据。AgentWrite 先规划各节字数，再逐节写。
  - 对 NovelFork：只有「按段规划字数」可借鉴，其余依赖微调，不适用 BYOK 场景。
  - 代码：Apache-2.0。

- **Ex3**（2024）https://arxiv.org/abs/2408.08506
  - 机制：从原著抽取结构，构造指令数据微调模型，再做树状扩写。
  - 对 NovelFork：依赖微调，不适用。「从既有小说抽取结构」可以和导入、拆文功能对照参考。
  - 代码：未核实。

- **DOME**（2024-12，NAACL）https://arxiv.org/abs/2412.13575
  - 机制：动态层级大纲，规划和写作交替进行；用时序知识图谱做记忆，并用时序冲突分析器评估一致性。
  - 结论：流畅度、连贯性优于基线（摘要层面的表述）。
  - 对 NovelFork：「大纲随写作动态修订」可借鉴。代价是 NstAgent 论文指出，KG 记忆即使在 1 万字规模也需要上千次 LLM 调用。
  - 代码：GitHub 未声明许可证，不能复用。

- **StoryWriter**（2025-06）https://arxiv.org/abs/2506.16445
  - 机制：大纲 agent 产出事件和事件关系；规划 agent 决定每章写哪些事件；写作 agent 按当前事件动态压缩历史。
  - 结论：质量和长度都优于基线。用它生成了约 6000 篇、平均 8000 词的数据集。
  - 对 NovelFork：「按当前事件压缩历史」就是按相关性做召回，而不是固定取近 N 章。
  - 代码：THU-KEG/StoryWriter 未声明许可证。

- **SCORE**（2025-03）https://arxiv.org/abs/2503.23512
  - 机制：跟踪关键物品状态，比如已毁物品不能无故再出现；生成分集摘要；用 TF-IDF + 向量的混合 RAG 找相关历史片段来检测不一致。
  - 结论：一致性优于 GPT 基线。具体数值只出现在二手来源里，未核实。
  - 对 NovelFork：「物品、状态守恒」规则可以直接加进 state 通道的检查。

- **NstAgent**（2026-09）https://arxiv.org/abs/2609.35759
  - 机制：维护三部分状态，即角色快照、过往事件、未来要求（伏笔、悬念、承诺）。每章只调一次 update；默认不注入前文正文，需要时用工具 `read(i)` 读全章、`search(q)` 做 BM25 检索、`correct(i,old,new)` 回改前文。
  - 结论：在 1 万到 10 万词范围内，一致性和写作质量都没有随长度明显退化；对照的滚动摘要基线存在压缩损失和事实漂移。作者用「固定只评最后约 1 万词」来规避评审模型在长文本上的疲劳。
  - 对 NovelFork：这是和「每章开销线性增长」最直接对口的方案。状态有界、按 key 关闭条目，提示词规模只取决于「提示 + 大纲 + 状态」。
  - 代码：MIT。

- **ConWriter**（2026，EMNLP Findings）https://arxiv.org/abs/2608.05169
  - 机制：静态记忆包括前提、世界规则、角色固有属性、风格、任务指令；动态记忆包括事件、实体状态、关系、时间、未解决约束。每个场景生成 Pre/Post/Forbid 转移算子，校验通过才提交；高不确定性片段优先校验；修复只改句子级补丁。召回用确定性过滤、新近度和固定 top-k 上限。
  - 结论：在 ConStory-Bench 上，3K/6K/12K 三个长度、多个模型下，表现持平或优于直接生成，并在一致性上优于 DOME。注意每个任务只测了前 5 个用例，样本很小。
  - 对 NovelFork：静态/动态的划分和经纬的 canon/dynamic 一一对应；Forbid 谓词可以替代正则检查。
  - 代码：MIT。

- **MAGNET**（2026-07）https://arxiv.org/abs/2607.00918
  - 机制：多个角色 agent 基于共享的结构化状态和目标序列提出行动，由 critic 精修。
  - 结论：在 20 页和 100 页的故事上优于 StoryWriter 等基线；消融实验显示 critic、结构化状态、目标序列都有显著贡献。
  - 对 NovelFork：可以作为 character-kernel 通道「角色按目标行动」的参考。
  - 代码：未核实。

### 2.2 层级摘要与记忆压缩

- **MemGPT / Letta**（2023）https://arxiv.org/abs/2310.08560
  - 机制：借鉴操作系统的虚拟内存，分层管理主上下文和外部存储，通过「中断」换入换出。Letta 的 memory block 常驻上下文，有 label、description、字符上限和 read_only 字段。
  - 对 NovelFork：可以学 block 的字符上限和只读标记。canon 层对模型只读，正好对应 read_only。
  - 代码：Apache-2.0。

- **RAPTOR**（2024）https://arxiv.org/abs/2401.18059
  - 机制：文本切成约 100 token 的块；先用 UMAP 降维，再用 GMM 软聚类（BIC 选簇数）；每簇做摘要，递归建树。
  - 结论：collapsed-tree 召回优于逐层遍历；配合 GPT-4 时 QuALITY 绝对提升 20%。
  - 对 NovelFork：小说本来就有章、卷、全书的天然层级，可以按章节结构建树，不需要聚类，比原方法更简单。
  - 代码：MIT。

- **ReadAgent**（2024）https://arxiv.org/abs/2402.09727
  - 机制：由 LLM 决定如何分页成 episode，每页压缩成 gist，需要细节时再回查原文页。
  - 结论：在 NarrativeQA（最长 34.3 万词）、QuALITY、QMSum 上都优于基线，有效上下文扩大 3.5–20 倍。
  - 对 NovelFork：「gist 常驻 + 按需回查原章」是 recent-summary 通道的升级方向。

- **MemoryBank**（2023）https://arxiv.org/abs/2305.10250
  - 机制：按艾宾浩斯遗忘曲线，随时间和重要度遗忘或强化记忆。
  - 对 NovelFork：不建议用于设定，见第 5 节。

- **Generative Agents**（2023）https://arxiv.org/abs/2304.03442
  - 机制：新近度按 0.995^小时 衰减，重要度由 LLM 打 1–10 分，相关度用 cosine；三项归一化后等权相加。重要度累计超过 150 时触发反思。
  - 对 NovelFork：见第 1 节第 7 条。

- **A-MEM**（2025，NeurIPS 2025）https://arxiv.org/abs/2502.12110
  - 机制：Zettelkasten 式笔记，每条记忆带关键词、标签和上下文描述，自动和相关旧笔记建链；新记忆进来可能触发旧记忆被改写（memory evolution）。
  - 对 NovelFork：可以借「自动建链」做设定条目之间的关联推荐。自动改写旧记忆和作者权威冲突，不能借。
  - 代码：MIT。

- **Zep / Graphiti**（2025）https://arxiv.org/abs/2501.13956
  - 机制：时序知识图谱，边上带有效期窗口；召回是语义 + BM25 + 图遍历的混合。
  - 结论：DMR 基准 94.8%，MemGPT 为 93.4%；LongMemEval 上准确率最多提升 18.5%，延迟降低 90%。
  - 对 NovelFork：见第 1 节第 5 条。

- **HippoRAG**（2024，NeurIPS）https://arxiv.org/abs/2405.14831
  - 机制：知识图谱 + Personalized PageRank 做多跳召回。
  - 结论：多跳 QA 最多提升 20%；单步召回比 IRCoT 便宜 10–30 倍、快 6–13 倍。
  - 对 NovelFork：可以在 SQLite 的实体关系表上用 PPR 做「关系扩散召回」，比如提到 A 时把和 A 强关联的伏笔也带上。
  - 代码：MIT。

- **GraphRAG**（2024）https://arxiv.org/abs/2404.16130
  - 机制：抽取实体图，预先生成社区摘要，用 map-reduce 回答全局问题。
  - 结论：在约 100 万 token 语料的全局问答上，全面性和多样性优于普通 RAG。
  - 对 NovelFork：「社区摘要」可以理解为「势力或人物圈子的摘要」，但全量抽取成本高。
  - 代码：MIT。

- **LightRAG**（2024）https://arxiv.org/abs/2410.05779
  - 机制：图和向量做双层召回（local / global / hybrid / naive / mix），支持增量更新。README 说明默认存储是内存加文件持久化，只适合测试。
  - 代码：MIT。

- **Mem0**（2025）https://arxiv.org/abs/2504.19413
  - 机制：抽取、合并、召回；图记忆变体只比基础配置高约 2%。
  - 结论：在 LOCOMO 上 LLM-judge 指标相对 OpenAI 提升 26%，p95 延迟降低 91%，token 节省超过 90%。
  - 对 NovelFork：「图记忆只带来约 2% 收益」说明不必上图数据库。

- **MemoryOS**（2025）https://arxiv.org/abs/2506.06326
  - 机制：短期、中期、长期三层；中期片段按访问频率等累积「热度」，超过阈值就升级为长期画像或知识。
  - 对 NovelFork：可以用热度阈值决定哪些 narrative_fact 进入待审候选，升级为经纬条目。
  - 代码：Apache-2.0。

- **MemOS**（2025）https://arxiv.org/abs/2507.03724
  - 机制：MemCube 封装记忆内容和元数据（来源、版本）。
  - 对 NovelFork：来源和版本元数据适合给机器写入的条目做审核和撤销。
  - 代码：Apache-2.0。

### 2.3 一致性检测与评测

- **ConStory-Bench**（2026-03）https://arxiv.org/abs/2603.05890
  - 内容：2000 条提示词，4 类任务；错误分 5 大类、19 子类；ConStory-Checker 为每条判断提供原文证据。
  - 发现：错误集中在事实和时间维度，多出现在叙事中段，出现在 token 熵较高的片段，部分错误类型会共现。
  - 对 NovelFork：中段 + 高熵这两个信号可以用来决定重点检查哪些段落。

- **FlawedFictions**（2025，COLM）https://arxiv.org/abs/2504.11900
  - 内容：可控地往人写故事里注入情节漏洞来评测模型。
  - 发现：最强的模型表现也很差，故事越长越差；LLM 生成的摘要和故事中，情节漏洞检出率比人写原文分别高 50% 以上和 100% 以上。
  - 对 NovelFork：说明摘要本身就会引入漏洞，层级摘要必须可审核、可回溯到原章节。

- **FABLES**（2024，COLM）https://arxiv.org/abs/2404.01261
  - 内容：对 26 本书的 LLM 摘要中 3158 条陈述做人工标注。
  - 发现：不忠实的陈述多涉及事件和角色状态，需要间接推理才能判伪；LLM 评审和人工标注的相关性都不强；摘要系统性地偏重书的结尾部分。
  - 对 NovelFork：卷摘要要防止偏重结尾，可以按章均匀抽取，或者先逐章摘要再合并。

- **NCP-Bench**（2026，ICML）https://arxiv.org/abs/2608.08160
  - 内容：用叙事承诺保持（Narrative Commitment Preservation）作为互动叙事的评测框架。
  - 发现：表现最好的 GPT-5.2 在 20 轮后存活率只有 42%，各模型的事实冲突率在 40%–68%。
  - 对 NovelFork：「承诺」可以显式建模并自动检查，这一点和伏笔台账一致。

- **WebNovelBench**（2025）https://arxiv.org/abs/2505.14818
  - 内容：4000 多部中文网文，从梗概生成故事；8 个维度由 LLM 评审打分，换算成相对人写作品的百分位。
  - 对 NovelFork：可以作为中文网文质量评估的参考。它不评测一致性。

- **NarrativeQA**：只作为 ReadAgent 的评测集出现，本次没有单独调研。

### 2.4 伏笔与情节线

- **CFPG**（2026-01）https://arxiv.org/abs/2601.07033
  - 机制：从 BookSum 语料中挖掘 Foreshadow–Trigger–Payoff 三元组，把伏笔编码成可执行的因果谓词。
  - 结论：payoff 准确率和叙事对齐都显著优于普通提示基线。
  - 补充：arXiv 上用 foreshadowing + story + LLM 检索，只命中这一篇。其他 plot thread tracking 的专门工作未找到，未核实。
- NstAgent 的 Future Requirements、ConWriter 的 Q_t（未解决约束）、NCP-Bench 的 commitments 是同一个思想：**伏笔 = 带 key 的未兑现承诺，必须显式开启、推进、关闭**。

各工具的共同点：
1. 普遍采用「写前读状态 → 写 → 校验 → 落地 → 状态回写」的闭环。
2. 伏笔做成显式的表或字段，而不是靠召回窗口碰运气。
3. 设定按条目、锚点、预算注入，并有常驻或 must 等级。
4. 机器写入的设定先进待确认区，或者整批可撤销。

NovelFork 已经有经纬审核和多通道打分。差距主要在第 2 点（伏笔台账的生命周期）、第 3 点（设定按相关性筛选）和闭环里的门禁强制性。

## 5. 不建议借鉴的东西

- **需要常驻服务**：
  - Graphiti/Zep 依赖 Neo4j、FalkorDB 或 Neptune，Kuzu 后端已标为弃用。
  - MemOS 自托管需要 Neo4j + Qdrant。
  - Letta 需要服务端。
  - mem0 自托管需要 docker compose 加向量库。
  - 马良写作依赖 Chroma 服务。
  - AI_NovelGenerator 依赖 MongoDB 副本集。
  - 这些都违反「单机 EXE、无重型服务」的约束。只借数据模型和算法。
- **Python 栈整体嵌入**：Cognee 和 LightRAG 虽然有本地嵌入式默认存储，但都是 Python 运行时，和 Bun 单 EXE 冲突。LightRAG 官方也说明默认存储不适合生产。
- **全量图谱抽取**：GraphRAG、LightRAG、DOME 每个文本块都要做实体关系抽取。NstAgent 论文指出，KG 记忆在 1 万词规模就要上千次 LLM 调用；mem0 论文显示图记忆只比基础配置高约 2%。对 300 万字的书来说，成本和收益不成比例。
- **自动改写或遗忘记忆，与「作者是权威」冲突**：
  - A-MEM 的 memory evolution 会自动改写旧笔记。
  - MemoryBank 按遗忘曲线衰减记忆，设定不能被遗忘。
  - Letta agent 会自主编辑 core block。
  - mem0 的自动抽取会直接写入。
  - 如果要借，只能借成「生成待审候选」，不能直接写 canon。
- **依赖微调**：Ex3、LongWriter、StoryWriter 的 SFT 部分不适用 BYOK 场景。
- **许可证不允许，只能学习机制，代码和提示词不能进仓库**：
  - AGPL-3.0：AI_NovelGenerator（及其衍生 NovelWriter_public、AI_NovelGenerator_ex）、NovelForge（RhythmicWave）、neuro-book。
  - GPL-3.0：webnovel-writer（及 opencode 版）、Pagekin / AI-Novel-Writer、RecurrentGPT、DaisyWriter。
  - 未声明许可证，默认保留所有权利：Long-Novel-GPT、THU-KEG/StoryWriter、DOME 官方仓库。
  - 许可证存疑：天命、马良写作。在许可证核实之前，按不能复用处理。
- **只用 LLM 评审做一致性裁决**：FABLES 显示 LLM 评审和人工标注的相关性都不强，FlawedFictions 显示最强模型的漏洞检测能力也很差。检查结果只能作为附证据的提示，交给作者裁决，不能自动修改正文。
