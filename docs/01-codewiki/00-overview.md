# NovelFork CodeWiki 总览

## 1. 目的

本 CodeWiki 的目标不是介绍功能清单，而是固定 NovelFork 当前已经定型的系统边界，避免后续继续长出新的中间概念。

写作模型的权威定义见：`docs/01-codewiki/architecture/canonical-writing-model.md`。

它回答四件事：

1. 系统现在有哪些稳定概念
2. 哪些概念已经废弃或正在收口
3. 哪些模块负责什么
4. 以后发生变更时，应该去哪里更新记录

## 2. 当前阶段

NovelFork 现在处于“做减法”阶段。

这意味着：

- 不再扩展新的写作中间态概念
- 不再把候选稿、草稿之类对象继续作为主产品概念维护
- 不再把双存储兼容当作长期架构
- 不再通过增加新层来解决旧层混乱

当前工作的重点是：

- 收口
- 删除
- 整理
- 固化

## 3. 稳定边界

### 3.1 静态层：经纬

经纬承担作者手工维护的静态参考资料。

包括但不限于：

- 人物设定
- 地点设定
- 世界规则
- 术语定义
- 势力关系
- 作者备注

这部分的特征是：

- 相对稳定
- 可人工维护
- 不应被动态写作过程频繁改写

### 3.2 动态层：叙事记忆

叙事记忆承担小说创作过程中的动态事实。

包括但不限于：

- 事件推进
- 角色状态变化
- 伏笔状态
- 时间线变化
- 关系变化
- 写作过程中的事实回写

这部分的特征是：

- 变化频繁
- 代表运行时真相
- 必须由写作动作持续更新

### 3.3 结果层：正式章节

正式章节保留为独立业务对象，但它不是中间态。

它是：

- 写作动作的最终结果
- 可发布、可展示、可回溯的成品
- 叙事变化后的稳定落点

### 3.4 配置层：预设 / 模板 / 节拍

这些属于用户可编辑的创作配置，不属于叙事事实。

包括：

- 写作预设
- 模板
- 节拍
- 风格配置

## 4. 工具层定位

工具不是对象工厂，工具是用户体验入口。

工具的职责是帮助用户完成写作动作、分析动作或配置动作，而不是继续生成一套新的业务实体。

典型工具包括：

- 文风提取
- 选段扩写
- 改写
- 多版本
- 章节结算相关动作

## 5. 当前要删除的东西

### 5.1 概念层

- 候选稿
- 草稿
- 候选稿生命周期
- 草稿生命周期
- 候选稿/草稿/章节三态并行模型
- 章节推进这一类模糊中间名词

### 5.2 存储层

- SQLite 作为章节资源主存储
- 文件系统 + SQLite 双主语义
- 兼容回退成为长期架构

### 5.3 工具层

- 以候选稿为核心命名的工具
- 依赖旧中间态的 accept/reject/archive 模型
- 不再符合当前边界的写作动作入口

## 6. 当前要整理的东西

### 6.1 保留并整理为稳定对象

- 正式章节
- 叙事记忆
- 经纬
- 预设
- 模板
- 节拍

### 6.2 保留并整理为工具

- 文风提取
- 选段扩写
- 改写
- 多版本
- 章节结算 / 发布 / 回写相关动作

## 7. 架构原则

1. 模块化单体，不做微服务拆分
2. 一个概念只保留一个主归属
3. 动态事实进入叙事记忆
4. 静态设定进入经纬
5. 正式章节作为最终结果保留
6. 工具服务于用户体验，不再制造新对象层
7. 文档必须可反查到代码，代码也必须能映射回文档

## 8. 文档组织

建议后续按照以下结构维护：

- `01-concepts/`：概念定义
- `02-workflows/`：写作与修订流程
- `03-tool-map/`：工具地图
- `04-storage-boundaries/`：存储边界
- `05-deletion-list.md`：删除清单
- `06-refactor-list.md`：整理清单
- `07-risk-register.md`：风险清单
- `08-decision-log.md`：决策日志
- `09-maintenance-rules.md`：维护规则

## 9. 维护规则

- 新功能先判断归属：工具层、配置层、事实层、结果层
- 删除旧概念必须同步写入删除清单
- 每次大调整必须更新决策日志
- 每次调整后检查文档是否仍能反查到代码

## 10. 结束语

这个 CodeWiki 的目标是让系统变得更轻，而不是更复杂。

如果某个新设计会重新制造一层中间对象，默认应当先拒绝，再确认是否真的必要。
