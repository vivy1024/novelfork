# 风险清单

## 1. 概念回流风险

### 表现

已经决定删除的候选稿 / 草稿概念，通过新工具、新 UI 或新 API 名称重新出现。

### 后果

- 对象模型再次变重
- 用户体验变复杂
- 文档和代码重新分叉

### 防护

- 新功能先判断归属
- 禁止新建 candidate / draft 主概念
- 定期搜索旧概念出现位置

## 2. 双存储风险

### 表现

SQLite 和文件系统同时承担章节正文主语义。

### 后果

- 数据不一致
- 测试复杂
- 工具实现变重
- 文档无法简单说明

### 防护

- 文件系统作为正式章节主存储
- SQLite 不再扩展章节资源主语义
- 兼容层必须有清理计划

## 3. 工具对象化风险

### 表现

工具不再只是动作，而是开始制造新的业务对象。

### 后果

- 候选稿/草稿以新名字复活
- 多版本变成另一个资源系统
- 用户感知变复杂

### 防护

- 工具输出必须明确去向
- 工具结果只允许进入正式章节、多版本、配置建议或叙事记忆事件

## 4. 叙事事实混入经纬风险

### 表现

动态事件、角色状态、伏笔进度被写入经纬。

### 后果

- 静态参考被污染
- 叙事记忆失去唯一性
- 后续召回混乱

### 防护

- 动态事实只进叙事记忆
- 经纬更新需要作者确认

## 5. 文档漂移风险

### 表现

CodeWiki 记录的边界与真实代码不一致。

### 后果

- 以后仍然需要重新人工梳理
- 决策被遗忘
- 旧概念重新出现

### 防护

- 大改后更新 CodeWiki
- 跑文档漂移检查
- 重要决策写入 `08-decision-log.md`

## 6. 过早微服务化风险

### 表现

为了让模块看起来清晰，把系统拆成多个微服务或大量外部 API。

### 后果

- 部署复杂度上升
- 调试成本上升
- 概念混乱被网络边界放大

### 防护

- 当前保持模块化单体
- 先收口概念与存储边界，再考虑服务边界
